# npm ERESOLVE and peer dependencies

`npm error ERESOLVE unable to resolve dependency tree` stops `npm install` before a single
package is written. Since npm 7, peer dependencies are installed automatically and a conflicting
peer range is a hard error — the class of failure that did not exist on npm 6.

```
npm error While resolving: my-app@1.0.0
npm error Found: react@18.3.1
npm error Could not resolve dependency:
npm error peer react@^19.0.0 from chart-lib@2.4.0
```

The line that matters is always `peer … from …`: the project decided one version, a dependency's
`peerDependencies` excludes it, and npm refuses to guess.

## Read the tree before choosing a flag

| Line | What it tells you |
| --- | --- |
| `While resolving:` | the package whose dependencies are being resolved |
| `Found:` | the version already chosen for that name, and who asked for it |
| `Could not resolve dependency:` | the package whose peer range excludes that version |

```bash
npm ls react                              # which versions exist, and who requires them
npm explain chart-lib                     # why the package is in the tree
npm view chart-lib peerDependencies --json
npm view chart-lib versions --json | tail -20
```

`npm view <pkg> peerDependencies` is the cheapest fix path: if a newer patch widened the range,
upgrading beats every override.

## Four strategies, in order worth trying

| Strategy | What it changes | Lockfile | Take it when |
| --- | --- | --- | --- |
| Upgrade the dependent | its `peerDependencies` range | clean | a release accepts your version — always first |
| `overrides` | resolution for the whole tree | clean, reproducible | a transitive package lags behind |
| `--legacy-peer-deps` | skips peer installation (npm 6 behaviour) | records the skipped peers | plugin ecosystem, migration in progress |
| `--force` | installs anyway, may duplicate | can hold duplicates and broken peers | never in CI; local unblock only |

`npm install --strict-peer-deps` is the inverse: it refuses to auto-pick when ranges conflict, which
is what you want in CI when you would rather fail than drift.

## overrides that actually apply

```json
{
  "dependencies": { "react": "^19.1.0", "chart-lib": "^2.4.0" },
  "overrides": { "chart-lib": { "react": "$react" } }
}
```

- `$react` means "the version the root manifest resolves", so the pin follows your own dependency
  instead of being copied in.
- The field applies to the whole tree, including packages you never import.
- **In a workspace, `overrides` in a package's own `package.json` is ignored.** Only the root
  counts:

```bash
npm pkg set 'overrides.react=$react' -w .    # writes the root manifest
npm install --workspaces
```

If two workspaces genuinely need different majors, they need separate lockfiles. No override
makes one `node_modules` hold two Reacts safely.

## When the tree is already installed

npm reuses an existing `node_modules`, so an `overrides` edit can silently fail to reach a nested
copy:

```bash
rm -rf node_modules package-lock.json && npm install
```

A merge that combined two lockfiles can raise `ERESOLVE` on a manifest that is fine. Inspect before
deleting anything:

```bash
npm ls --all 2>&1 | grep -i "invalid\|peer\|ERR"
npm install --package-lock-only    # does the manifest resolve at all?
```

`npm ci` is the only command that promises "exactly this lockfile or nothing" — use it in CI and
`npm install` locally.

## Beware of the containment strategies

- `--legacy-peer-deps` typed once in one terminal is not recorded anywhere. The next person's
  `npm ci` fails the same way; put it in `.npmrc` or remove the need for it.
- `--force` resolves the conflict by installing conflicting copies; the failure resurfaces at
  runtime as two React instances, a dead context, or an invalid hook call.
- `peerDependenciesMeta: { optional: true }` means npm 7+ does not fail when the peer is absent.
  An `ERESOLVE` naming an *optional* peer usually points at a second, real conflict above it.
- A `yarn.lock` next to a `package-lock.json` produces two disagreeing resolutions. Commit one,
  delete the other.
- Node 20 ships npm 10 and Node 18 ships npm 9; the error text and resolution details differ. Pin
  the Node version in CI and in `.nvmrc`.

## Version cheat sheet

| npm | Peer dependencies | Conflict result |
| --- | --- | --- |
| 6 | warnings only, not installed | `npm WARN`, working tree |
| 7 | installed automatically | `ERESOLVE` (introduced here) |
| 8 | installed automatically, `overrides` supported | `ERESOLVE`, fixed by `overrides` |
| 8.3+ | `$package` references inside `overrides` | pin to the root's own version |
| 9 / 10 / 11 | same rules, `npm error` prefixes | richer `Could not resolve` text |

A `package-lock.json` generated by npm 6 will not reproduce on npm 10, because npm 6 never recorded
the peers it skipped.

## Global installs and npx

`npm install -g some-cli` resolves peers too, and a global prefix has no `overrides` field. Use
`npx` / `npm exec` for one-off tools and keep globals to packages with no peers:

```bash
npx some-cli@latest --version
npm exec --package=some-cli@latest -- some-cli --help
```
